# v7：无有效三消交换也可通关

## 方案审批

**批准主 Agent 提交的 v7 规则方案进入实现。** 最新用户要求覆盖旧的“必须清空所有宝石”唯一胜利条件。判定应为：正在游戏、HP>0、交换/下落/连锁/系统恢复均已结束，且现有三连已先处理；此时剩余宝石为0，或真实合法交换列表为空，即获胜。后者记 `reason='no-moves'`，保留真实剩余数量和颜色，不消除、不假报全清，不要求玩家先消耗重排。

规则不限于恰好4颗不同颜色：1颗、2颗、4颗、更多颗，只要落稳后确实没有任何能形成三消的相邻交换，都适用。反过来，无法求出“全清解”、提示搜索超时、金子未排通或当前没有自动三连，都不等于没有合法交换，不能据此提前获胜。必须用 `M.legal(board)` 的局部有效交换判定，而不是 `solveClear()` 是否返回解。

此处是规则与实现范围批准，尚不代表成品通过或发布。当前不沿用 v6 分数；实现后需新规则的实际输入、结果文案和边界验证。

## 状态边界

- 先完成既有 matches、交换回退、真实落砖及自动连锁；不能在消除动画中间、逻辑源棋盘临时无步时抢先弹胜利。
- 前槽恢复必须完成才检测胜利；已完成恢复后仍在槽内运输的石头不是交换锁，不必等其全部排完。获胜后保持既有前槽连续排出行为和守恒。
- HP0 仍失败；同一物理步内先已生效的致命碰刺不能被无步胜利覆盖。ready、主动暂停、结果已显示等状态不重复判定/重复播放奖励。
- 获胜关闭主源、停止危险时钟，保留 HUD 的真实剩余宝石数。no-moves 结果应明确“已无有效三消交换，国王获救；剩余 N 颗宝石”，不能仍写“全部 X 颗已清空”。
- 重排保留为游戏进行中的可选工具，不能成为无步盘的通关前置步骤，也不能在本应自动获胜的下一帧前消耗次数。正常还有有效交换的6颗尾盘继续游戏。
- 全清与无步两种结果均可正常下一关、重玩、选关及刷新；原 HP 危险、高能、前槽恢复和其他游戏不因这项规则变更改动。

## 已定位的文案与测试更新点

`game.js` 的 ready-description、初始 status、hint 空结果、stalled 通知、result-detail 和结果 status；`levels.js` 两关 lesson；`renderer.js` 国王胜利台词；`index.html` 皇家救援手册的胜利小节和一两颗必须重来说明均需同步。可以继续介绍全清作为一种胜利方式，但不能保留“才获胜”的排他语气。

另发现 `index.html` 手册还残留“通道堵死则提示重来”。这已被 v6 用户要求覆盖，属于漏改的陈旧文案，本次必须改为自动前置集金槽疏通、系统恢复期间国王安全等待。不能一边移除无步强制重来，一边继续宣传内部卡住也要求重来。

## 新验收清单

1. 构造落稳的4颗不同宝石无步局，立即no-moves胜利，HP及4颗宝石保持，供料关闭，重排次数未扣。
2. 1/2颗以及较多颗无合法交换均胜利；有合法交换但无全清解的残局继续；全清仍以原分支胜利。
3. 暂时无合法交换但已有横/竖三连时，必须先消除/落砖/连锁，再判断；交换、落砖或恢复中不得提前胜利。
4. 六颗正常尾盘有合法交换，保留5秒仍playing；排金再多也不单独触发胜利。
5. HP0与无步同时存在仍失败，胜利后不继续伤害；下一关/重来/刷新无旧reason和旧结果残留。
6. 至少一条真实鼠标或触控路线产生剩余宝石的无步胜利，保存最终棋盘、M.legal为空的只读证据、结果文案和下一关实际输入。构造引擎单测不能冒充真实玩家路线。
7. 正常两关全清、v6真实卡死恢复、守恒与碰撞、移动端结果层均保留回归。若实际规则/教程仍出现“只剩一两颗必须重来”或“通道堵死请重来”，视为未完成。

最终由制作人据新规则证据审批成品，批准发布与实际上线继续分开记录。
